## Сценарии

- Проверка RSA-подписи JWT, issuer/audience/expiry/iat/id/azp, PKCE RFC7636, state, привязки браузера, срока и повторного callback. Числовой Telegram `id` не путается с OIDC `sub`.
- Запрос token endpoint действительно формируется с HTTP Basic, code verifier и правильным redirect URI; JWKS проверяется с контролируемым HTTP transport.
- Создание/публикация конкурса через HTTP → две заявки → два чека → два одобрения → участники #1/#2 → открытие ТЗ → сдача ZIP → заморозка/возобновление → обновление работы → завершение → оценка A → запрет преждевременной публикации → оценка B → публикация → призы и личные результаты.
- Повторное одобрение запрещено; отклонение с причиной и повторный чек работают; кнопка со старой версией чека недействительна.
- Оценки/комментарии скрыты до публикации, затем зафиксированы. Проверены средняя оценка и все tie-break критерии.
- После дедлайна изменения отвергаются сервером даже без планировщика. Отмена блокирует платежи и результаты; показывается информация о возврате.
- CSRF/Origin, обычный пользователь против Admin, XSS escaping, доступ к чужим чекам/ZIP/работам, лимит HTTP body, приватные storage paths.
- Проверка реальных PNG/PDF/ZIP, расширения/MIME, traversal, symlinks, ZIP bombs, ограничений размера.
- Локальное сохранение/чтение/удаление и S3 API adapter с проверкой параметров через Botocore Stubber.
- Очередь Telegram: отправка текста/чека с кнопками через записывающий тестовый транспорт, изоляция ошибок, повтор, истёкший lease, защита от завершения устаревшим worker.
- Удаление OAuth query из access logs.

## Что не проверялось живым подключением

1. **PostgreSQL/Neon:** в этой среде нет доступного нативного PostgreSQL сервера. Два теста одновременного одобрения пропущены локально. Они включены в GitHub Actions с PostgreSQL 17. Миграция выполнена на SQLite и сгенерирована в SQL PostgreSQL, но это не заменяет запуск `alembic upgrade head` на вашей PostgreSQL БД.
2. **Telegram:** реальные client credentials, Telegram login и отправка сообщений вашему боту не проверялись. Внешние вызовы в тестах контролируемые, с локально подписанными JWT и записывающим получателем.
3. **S3/R2, Raven Host, Cloudflare и домен:** действительные credentials и хостинг не предоставлены; реальные подключение, deploy, TLS и DNS не выполнялись.
4. **Устройства:** вёрстка проверена Chromium при мобильных размерах. Физические Android/iPhone и Safari не запускались.
5. **Docker/systemd/CI:** файлы подготовлены; сборка контейнера, запуск systemd и GitHub Actions в этой среде не выполнялись.

Один warning тестов относится к переходу установленной версии Starlette TestClient с httpx на httpx2. Текущий тестовый интерфейс работает; production-код использует обычный HTTPX AsyncClient и не импортирует TestClient.

## Как повторить

```bash
pip install -r requirements-dev.txt
pytest -q
ruff check app bot tests scripts
python -m compileall -q app bot alembic
playwright install chromium
python tests/ui_smoke.py
```

`tests/ui_smoke.py` создаёт временную БД с проверочными данными, запускает настоящий Uvicorn на локальном порту 17773 и Chromium. Рабочий `.env` не используется; тестовые данные не включены в production-приложение. Скриншоты по умолчанию сохраняются в `/tmp/nexviro-ui`; путь задаётся через `UI_ARTIFACT_DIR` (на Windows укажите подходящий каталог). Для своего Chromium можно задать `CHROMIUM_EXECUTABLE`.

Для PostgreSQL задайте `TEST_DATABASE_URL` на отдельную базу **nexviro_test** и запустите `pytest -q`. Содержимое этой тестовой базы очищается между тестами. После настройки production выполните `python scripts/check_config.py` и один контрольный цикл с собственным ботом до открытия платного конкурса.
